# 1. Fundamentos: qué problema resolvemos

Una aplicación sin persistencia pierde sus registros al reiniciarse. Una base de datos relacional permite almacenar datos de forma duradera, establecer restricciones y consultarlos mediante SQL. PostgreSQL es el motor; Supabase aloja y administra una instancia PostgreSQL. En esta práctica NO consumiremos la API REST de Supabase: Spring Boot se conecta directamente al motor mediante JDBC.

| Componente                | Responsabilidad                                                          |
|---------------------------|--------------------------------------------------------------------------|
| PostgreSQL                | Almacena filas y columnas; ejecuta SQL y mantiene restricciones.         |
| Supabase                  | Ofrece proyecto administrado, editor SQL, credenciales y panel de datos. |
| JDBC                      | Interfaz Java y controlador PostgreSQL para comunicarse con el servidor. |
| JPA / Jakarta Persistence | Define cómo mapear objetos Java a tablas mediante anotaciones.           |
| Hibernate                 | Implementa JPA, genera SQL y administra entidades.                       |
| Spring Data JPA           | Provee interfaces Repository y métodos como save, findAll y findById.    |
| Spring Boot               | Configura componentes, dependencias y arranque de la aplicación.         |

Secuencia de una petición: Postman → HTTP → EstudianteController → EstudianteService → EstudianteRepository → Hibernate/JDBC → PostgreSQL (Supabase). La respuesta vuelve en dirección contraria, normalmente en JSON.

# 2. ¿Qué hace cada capa?

- Controller: define rutas HTTP, recibe JSON y decide códigos de respuesta. No debería escribir SQL.

- Service: aplica reglas de negocio; por ejemplo, impedir correos duplicados o decidir qué sucede si no existe un ID.

- Repository: interfaz que extiende JpaRepository; Spring genera su implementación durante el arranque.

- Entity: objeto Java cuyo estado se mapea a una tabla. Entity no es sinónimo de JSON de entrada; en proyectos grandes se usan DTO.

Pregunta motivadora: si elimino la clase Repository, ¿quién ejecuta las operaciones de base de datos? Respuesta: necesitaría programarlas con otra capa de persistencia (por ejemplo JDBC manual).

# 3. Preparar la base de datos en Supabase

1.  Ingresar a https://supabase.com/ y crear una cuenta, si aún no existe.

2.  Crear un proyecto nuevo, definir nombre y contraseña fuerte de base de datos. Guardar la contraseña fuera del repositorio.

3.  Abrir SQL Editor y ejecutar el script mostrado a continuación. Para fines docentes trabajaremos en el esquema public.

create table if not exists public.estudiantes (

id bigint generated by default as identity primary key,

nombre varchar(80) not null,

apellido varchar(80) not null,

correo varchar(160) not null unique,

programa varchar(100) not null

);

Se escoge IDENTITY porque PostgreSQL genera el identificador. La restricción UNIQUE sobre correo protege también frente a dos solicitudes simultáneas que intenten insertar el mismo correo. Si la tabla ya existe y su estructura es distinta, IF NOT EXISTS no la modifica.

4.  En el panel de Supabase, abrir Connect → Session pooler. Copiar exactamente host, puerto, nombre de base de datos y usuario mostrados por el proyecto.

5.  Usar Session pooler, puerto 5432, para este backend de larga vida cuando la red solo tenga IPv4. La conexión directa también sirve si el entorno admite IPv6. No confundir con Transaction pooler (habitualmente 6543).

6.  Abrir Table Editor → estudiantes para verificar posteriormente las operaciones del programa.

IMPORTANTE: el usuario de Session pooler suele tener la forma postgres.\<PROJECT_REF\>; no es necesariamente solo postgres. El host pooler cambia entre proyectos y debe copiarse del panel. La clave anon/publishable y la service_role key NO se usan para esta conexión JDBC.

Usar sslmode=require cifra la conexión, pero no verifica completamente la identidad del servidor; para producción valorar verify-full y certificado CA.

# 7. Crear la entidad Estudiante

package com.ejemplo.estudiantes.model;

import jakarta.persistence.\*;

import jakarta.validation.constraints.Email;

import jakarta.validation.constraints.NotBlank;

import jakarta.validation.constraints.Size;

@Entity

@Table(name = "estudiantes", schema = "public")

public class Estudiante {

@Id

@GeneratedValue(strategy = GenerationType.IDENTITY)

private Long id;

@NotBlank @Size(max = 80)

@Column(nullable = false, length = 80)

private String nombre;

@NotBlank @Size(max = 80)

@Column(nullable = false, length = 80)

private String apellido;

@NotBlank @Email @Size(max = 160)

@Column(nullable = false, unique = true, length = 160)

private String correo;

@NotBlank @Size(max = 100)

@Column(nullable = false, length = 100)

private String programa;

public Estudiante() {}

// Generar getters y setters para los cinco campos desde el IDE.

}

Explicar: @Entity activa el mapeo; @Table elige tabla; @Id es clave primaria; @GeneratedValue indica generación por PostgreSQL; @Column describe restricciones; @NotBlank, @Email y @Size validan entrada Java cuando el controlador usa @Valid. Para ejecutar el proyecto, generar TODOS los getters y setters con el IDE (o escribirlos). No incluir un setter público de id en el JSON de creación.

# 8. Crear el Repository

package com.ejemplo.estudiantes.repository;

import com.ejemplo.estudiantes.model.Estudiante;

import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;

public interface EstudianteRepository extends JpaRepository\<Estudiante, Long\> {

boolean existsByCorreoIgnoreCase(String correo);

List\<Estudiante\> findByProgramaContainingIgnoreCase(String programa);

}

JpaRepository\<Estudiante, Long\>: el primer tipo es la entidad y el segundo es el tipo de la clave primaria. No hay una clase que implemente esta interfaz manualmente: Spring crea un proxy. Los nombres de métodos se convierten en consultas derivadas. El UNIQUE de PostgreSQL aplica igualdad según la colación: existsByCorreoIgnoreCase es solo una validación previa y no sustituye la restricción de base de datos; no garantiza unicidad case-insensitive.

# 9. Implementar Service: reglas y operaciones

package com.ejemplo.estudiantes.service;

import com.ejemplo.estudiantes.model.Estudiante;

import com.ejemplo.estudiantes.repository.EstudianteRepository;

import com.ejemplo.estudiantes.exception.RecursoNoEncontradoException;

import org.springframework.dao.DataIntegrityViolationException;

import org.springframework.stereotype.Service;

import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service

public class EstudianteService {

private final EstudianteRepository repo;

public EstudianteService(EstudianteRepository repo) { this.repo = repo; }

@Transactional(readOnly = true)

public List\<Estudiante\> listar() { return repo.findAll(); }

@Transactional(readOnly = true)

public Estudiante consultar(Long id) {

return repo.findById(id).orElseThrow(

() -\> new RecursoNoEncontradoException("Estudiante no encontrado: " + id));

}

@Transactional

public Estudiante crear(Estudiante nuevo) {

nuevo.setId(null);

if (repo.existsByCorreoIgnoreCase(nuevo.getCorreo()))

throw new DataIntegrityViolationException("El correo ya existe");

return repo.saveAndFlush(nuevo);

}

@Transactional

public Estudiante actualizar(Long id, Estudiante datos) {

Estudiante actual = consultar(id);

actual.setNombre(datos.getNombre());

actual.setApellido(datos.getApellido());

actual.setCorreo(datos.getCorreo());

actual.setPrograma(datos.getPrograma());

return repo.saveAndFlush(actual);

}

@Transactional

public void eliminar(Long id) {

Estudiante actual = consultar(id);

repo.delete(actual);

}

@Transactional(readOnly = true)

public List\<Estudiante\> buscar(String programa) {

return repo.findByProgramaContainingIgnoreCase(programa);

}

}

La inyección de dependencias ocurre en el constructor: Spring entrega el bean Repository al Service. @Transactional agrupa cambios dentro de una transacción; readOnly=true expresa intención de solo lectura. En actualizar se recupera una entidad administrada y se modifica; saveAndFlush fuerza sincronización con la base dentro de la transacción (no equivale a commit).

// exception/ApiExceptionHandler.java

package com.ejemplo.estudiantes.exception;

import org.springframework.http.HttpStatus;

import org.springframework.http.ResponseEntity;

import org.springframework.web.bind.MethodArgumentNotValidException;

import org.springframework.web.bind.annotation.ExceptionHandler;

import org.springframework.web.bind.annotation.RestControllerAdvice;

import org.springframework.dao.DataIntegrityViolationException;

import java.util.Map;

@RestControllerAdvice

public class ApiExceptionHandler {

@ExceptionHandler(RecursoNoEncontradoException.class)

public ResponseEntity\<?\> noExiste(RecursoNoEncontradoException e) {

return ResponseEntity.status(HttpStatus.NOT_FOUND)

.body(Map.of("error", e.getMessage()));

}

@ExceptionHandler(DataIntegrityViolationException.class)

public ResponseEntity\<?\> conflicto(DataIntegrityViolationException e) {

return ResponseEntity.status(HttpStatus.CONFLICT)

.body(Map.of("error", "Conflicto con restricciones de datos"));

}

@ExceptionHandler(MethodArgumentNotValidException.class)

public ResponseEntity\<?\> validacion(MethodArgumentNotValidException e) {

return ResponseEntity.badRequest()

.body(Map.of("error", "Datos de entrada no válidos"));

}

}

Para una aplicación real se deben distinguir otras restricciones de integridad y devolver errores por campo, registrar incidencias y usar DTO de entrada/salida; aquí se simplifica para destacar persistencia.

# 11. Implementar Controller: endpoints REST

package com.ejemplo.estudiantes.controller;

import com.ejemplo.estudiantes.model.Estudiante;

import com.ejemplo.estudiantes.service.EstudianteService;

import jakarta.validation.Valid;

import org.springframework.http.HttpStatus;

import org.springframework.http.ResponseEntity;

import org.springframework.web.bind.annotation.\*;

import java.util.List;

@RestController

@RequestMapping("/api/estudiantes")

public class EstudianteController {

private final EstudianteService service;

public EstudianteController(EstudianteService service) {

this.service = service;

}

@GetMapping

public List\<Estudiante\> listar() { return service.listar(); }

@GetMapping("/{id}")

public Estudiante consultar(@PathVariable Long id) {

return service.consultar(id);

}

@PostMapping

public ResponseEntity\<Estudiante\> crear(@Valid @RequestBody Estudiante e) {

return ResponseEntity.status(HttpStatus.CREATED).body(service.crear(e));

}

@PutMapping("/{id}")

public Estudiante actualizar(@PathVariable Long id,

@Valid @RequestBody Estudiante e) {

return service.actualizar(id, e);

}

@DeleteMapping("/{id}")

@ResponseStatus(HttpStatus.NO_CONTENT)

public void eliminar(@PathVariable Long id) { service.eliminar(id); }

@GetMapping("/buscar")

public List\<Estudiante\> buscar(@RequestParam String programa) {

return service.buscar(programa);

}

}

Diferenciar @RequestBody (JSON), @PathVariable (valor de la URL), @RequestParam (parámetro ?programa=...), @Valid (dispara validación) y ResponseEntity (status y contenido).

# 13. ¿Qué pasa internamente cuando llamamos save()?

7.  Spring MVC convierte el JSON a objeto Estudiante mediante Jackson.

8.  @Valid revisa reglas de entrada; si falla retorna 400 a través del handler.

9.  Controller invoca Service; Service valida y pide guardar al Repository.

10. Spring Data JPA delega en Hibernate; al persistir, Hibernate genera INSERT y recupera el identificador.

11. JDBC envía la sentencia por la conexión TLS a PostgreSQL en Supabase.

12. PostgreSQL valida NOT NULL, UNIQUE, tipos de datos y confirma la transacción.

13. La API devuelve 201 y un JSON con ID, que se puede comprobar en Table Editor.

Distinción didáctica: save() no significa «escribir un archivo JSON»; significa trabajar sobre entidades persistentes que Hibernate sincroniza con una base relacional. Algunas sentencias se ejecutan al flush/commit, no necesariamente en la línea exacta de save().

# 14. Métodos principales de JpaRepository

| Método                | Uso habitual                                                             |
|-----------------------|--------------------------------------------------------------------------|
| save(entidad)         | Persistir entidad nueva o fusionar estado de una existente según JPA.    |
| findAll()             | Traer todos los registros; no conviene sin paginación en tablas grandes. |
| findById(id)          | Retorna Optional\<T\>; puede estar vacío.                                |
| existsById(id)        | Comprobar existencia por identificador.                                  |
| delete(entidad)       | Programar eliminación de una entidad.                                    |
| count()               | Contar registros.                                                        |
| findAll(Pageable)     | Consulta paginada.                                                       |
| saveAndFlush(entidad) | Guardar y forzar sincronización SQL con la BD en ese momento.            |

# 15. Consultas derivadas, SQL y JPQL

Spring Data interpreta los nombres de métodos usando propiedades de la entidad, no nombres arbitrarios de columnas SQL. Ejemplo: findByProgramaContainingIgnoreCase(String programa) busca coincidencias parciales sin distinguir mayúsculas.

// Agregar a EstudianteRepository:

List\<Estudiante\> findByApellidoIgnoreCase(String apellido);

long countByProgramaIgnoreCase(String programa);

// Alternativa con JPQL:

@Query("select e from Estudiante e where lower(e.programa) = lower(:programa)")

List\<Estudiante\> buscarProgramaExacto(@Param("programa") String programa);

Para usar @Query/@Param, importar org.springframework.data.jpa.repository.Query y org.springframework.data.repository.query.Param. JPQL referencia la clase Estudiante y su propiedad programa; SQL nativo referencia la tabla public.estudiantes y la columna programa.

# 16. Seguridad y consideraciones de Supabase

- Nunca incluir DB_PASSWORD, URL con contraseña ni claves administrativas en código, capturas, archivos compartidos o repositorios Git.

- El backend actúa con los permisos del rol PostgreSQL configurado. La seguridad de la API depende también de autenticar/autorización HTTP; conectar con contraseña de base de datos no protege endpoints públicos.

- En esta práctica no usaremos el cliente JavaScript ni PostgREST de Supabase. Son otras alternativas, no el camino Spring Data JPA.

- RLS de Supabase no sustituye la seguridad de esta API: sus políticas dependen del rol y del contexto de autenticación SQL. El usuario administrativo postgres normalmente puede evitar RLS; para producción, crear rol con privilegios mínimos y definir el esquema de seguridad.

- Mantener pool de conexiones pequeño para laboratorios; muchos alumnos creando aplicaciones paralelas pueden agotar límites del proyecto compartido.

- Para producción usar migraciones (Flyway/Liquibase), DTO, autenticación, registro de auditoría y gestión de secretos.

# 17. Errores frecuentes y solución

| Síntoma                              | Causa probable / prueba                                                               |
|--------------------------------------|---------------------------------------------------------------------------------------|
| Connection refused / timeout         | Host o puerto incorrecto, red bloqueada, proyecto pausado. Copiar Connect de nuevo.   |
| UnknownHostException                 | Se usó un host de ejemplo en lugar del host real de Supabase.                         |
| password authentication failed       | Usuario incorrecto (falta .PROJECT_REF), contraseña equivocada o variable no cargada. |
| Network is unreachable en db.\<ref\> | Conexión directa IPv6 desde red IPv4: utilizar Session pooler.                        |
| Schema-validation: missing table     | No se ejecutó SQL, tabla en otro esquema o nombre distinto.                           |
| relation estudiantes does not exist  | Tabla ausente; confirmar public.estudiantes.                                          |
| DataIntegrityViolationException      | Violación de UNIQUE o NOT NULL; revisar payload y datos existentes.                   |
| Port 8080 already in use             | Cambiar server.port o liberar el proceso.                                             |
| 400 Bad Request                      | JSON inválido, campo obligatorio vacío, correo mal formado o Content-Type ausente.    |
| 500 Internal Server Error            | Revisar stacktrace del servidor y log de SQL; no exponer detalles al cliente.         |
